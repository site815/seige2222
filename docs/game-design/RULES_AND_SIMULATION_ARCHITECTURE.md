# seige2222 — Rules and Simulation Architecture

[Design index](README.md) · [Status definitions](README.md#design-status)

The user has authorized native Unreal development, a playable single-player build, packaging, and a GitHub push. This document records implementation direction and architectural recommendations. The specific verified milestones and remaining checks are tracked in [First Playable Scope](FIRST_PLAYABLE_SCOPE.md); architectural descriptions alone are not completion claims.

## Chosen direction and current limits

**Confirmed user requirement:** Gameplay content and numerical rules must live in editable files outside the main engine execution code. Resource/building values, recipe inputs and outputs, timing, costs, rates, and balance should be changeable without rewriting the simulation's ordinary execution paths.

**Selected development environment:** Native Unreal Engine 5.8.3 on Windows. The initial implementation is single-player. Persistent multiplayer remains the gameplay design baseline and a later implementation stage; there is no claim that networking, authoritative servers, offline progression, or cross-server relocation already work.

**Implementation approach:** Separate data definitions, mutable simulation state, and presentation. Use generic mechanisms to execute external definitions. Concrete prototype choices are reversible implementation assumptions until reviewed; they do not silently settle the full game's open mechanics.

## Responsibilities

| Layer | Responsibility | Keep outside it |
| --- | --- | --- |
| Editable definitions | Resource and item identities, building capabilities, recipes, rates, costs, scenario setup, and numerical tuning | Live colony inventories, current orders, and player-owned runtime state |
| Loading and validation | Parse definitions, resolve IDs, check units/ranges, and report invalid content before starting the scenario | Hidden replacement balance values that disguise broken definitions |
| Simulation state | Buildings, stock by location, robots/workforce, jobs, cargo in transit, health, threats, and elapsed simulation time as supported by the slice | Rendering objects as the only copy of economically important state |
| Generic simulation execution | Apply construction commands and advance the supported staffing, production, transport, repair, and combat rules | A separate hardcoded behavior branch for every resource, recipe, or building |
| Unreal presentation and input | Render the current state, display explanations, select/place buildings, and submit player commands | Awarding production or moving inventory merely because an animation finished |
| Persistence and future authority | Save/load versioned state locally; later validate and own shared outcomes in the selected server design | An assumption that client-local simulation is sufficient authority for multiplayer |

The table expresses the intended separation. Only systems included in [First Playable Scope](FIRST_PLAYABLE_SCOPE.md) belong in the initial implementation. A named layer is not evidence that a full implementation exists.

## Definitions and supported behavior

**Current prototype files:**

| Folder | Definitions and responsibility |
| --- | --- |
| `Rules` | [Resources](../../Rules/resources.json), [recipes](../../Rules/recipes.json), [buildings](../../Rules/buildings.json), [policies](../../Rules/policies.json), [scenario](../../Rules/scenario.json), and [transport](../../Rules/transport.json) define the shared economy, simulation tuning, threats, initial stock, and deposit template. |
| `AIFILES` | [Colony controller](../../AIFILES/colony_ai.json) priorities, timing, and placement search; an explicit [established-colony manifest](../../AIFILES/developed_start.json), separate from the player/Starting-AI finite kit. The separate folder is a confirmed user requirement. After initialization, AI orders pay ordinary costs and use the same simulation. |
| `Interface` | [ui.json](../../Interface/ui.json) defines construction groups and shortcuts, resource-overlay references, descriptions, and credits. These are presentation definitions, not a second economy. |
| `Graphics` | [scene.json](../../Graphics/scene.json) defines logical-to-rendered scale, camera pitch/zoom/clearance and orbit sensitivity, regional-view threshold, terrain relief/pads, terrain/cloud materials and lighting, bounded vegetation counts/scales, and ten nature-asset roles. It does not replace logical simulation values. |

All four use explicit versions. Catalog records have stable IDs; policies contain numerical tuning and selectors for supported behaviors. New types of behavior can require code; changing supported content and balance must not require rewriting engine execution. See [Scenario and AI Setup](SCENARIO_AND_AI_SETUP.md), [Graphics and Interface Milestone 0.4](GRAPHICS_MILESTONE_0_4.md), and [First Playable Scope](FIRST_PLAYABLE_SCOPE.md) for represented behavior and verification boundaries.

**Definition contract:**

- Use stable IDs for resources, products, buildings, recipes, and scenarios. Display names can change without becoming save-file keys.
- A building declares capabilities and refers to recipes. A recipe declares its input/output quantities and duration. The simulation applies the same transaction rules to all definitions using that mechanism.
- Store rate ceilings, worker demand, health, repair inputs, ranges, movement speeds, and threat tuning in external data where those systems are implemented.
- Keep starting stocks and placed assets in scenario data, separate from universal item definitions.
- State units explicitly: quantity, transport capacity, distance, simulation time, and any real-time conversion. A number alone does not establish which clock a timer uses.
- Preserve actual locations for inventory and cargo. The prototype already keeps building inventories and courier cargo separately; a definition ID is not a colony-wide teleporting inventory.
- Define the permitted behavior vocabulary in code or a validated schema. Editing numbers or composing existing behaviors should not require engine changes; inventing a new simulation mechanism can require a code extension.

Do not place executable arbitrary scripts in balance files merely to satisfy the external-data requirement. A declarative format is sufficient for the initial resource, production, workforce, and threat systems.

### Current v0.9 worker, calendar, construction and save schema

Versioned economic Rules now use `prototype-9.0`. [workers.json](../../Rules/workers.json) owns finite-pool scheduling, body clearance, deployment, hauling mass/volume and task timing. [calendar.json](../../Rules/calendar.json) owns the shared integer-microsecond day/night and seasonal clock. Schema-1 [environment.json](../../Rules/environment.json) supplies world-offset-aware dry ground, water and landforms to both headless simulation and presentation. One `extraction_mine` definition replaces the eight resource-specific extractors; its saved deposit ID determines output and its external `extraction_rates` map determines the resource-specific rate. Only one living mine can bind to a deposit. [transport.json](../../Rules/transport.json) owns walking speed/physical units, access and path clearances, road constraints and the road/rail/vacuum tier chain with speed, width, labor, duration and incremental material costs. Buildings distinguish square body and reserved half-widths, declare edge access directions and explicitly opt into core deployment defense. Ordered phase names/thresholds live in policies under `phased_physical_delivery`.

The current `workers.json` policy is `logistics_scaling_policy: completed_facilities`, with `logistics_workers: 1`, `logistics_facilities_per_worker: 4`, `logistics_max_workers: 8` and `logistics_excluded_roles: [core, wall]`. `LogisticsJobs` derives `min(8, 1 + floor(eligible facilities / 4))` from living, enabled, completed buildings whose roles are not excluded. Power, staffing and supply state do not affect eligibility; sites and roads do not inflate the count. The same function adds logistics demand to `TotalJobs` and protects idle/working haulers from ordinary job reassignment, while essential core/service staffing retains precedence. Self-transfer couriers do not count as working haulers. This is a desired reserve, not a cap that cancels active deliveries. Paid manufacturing, physical reactivation and normal support still supply bodies. The current implementation has compiled; dedicated native and full-scenario acceptance are pending.

Construction reservations cover eligible completed source inventories after operating buffers. A hauling task reserves cargo before pickup and debits its actual source only as the identified body loads it. That same body follows a saved route to the actual destination port. Individual assigned builders must arrive before progress transfers proportional delivered stock into `InstalledMaterials`; the complete bill need not arrive before any work starts. Road upgrades retain earlier installed infrastructure and the previous tier's service while new materials/work accumulate. This supersedes the earlier core-only, full-bill and presentation-only port rules.

**Candidate dispatch policy:** [policies.json](../../Rules/policies.json) owns `delivery_priority_order`, defaulting to `fuel`, `maintenance`, `repair`, `defense`, `construction`, `production`, `trade`, `reserve`, `storage`, and `delivery_refill_trigger_fraction`, provisionally **0.5**. The next available body serves eligible requests in that order. Shared local and incoming stock is accounted against higher-priority targets before a lower class uses it; there are no extra cargo buckets. Standing buffers replenish at or below the half-target low-water mark and aim toward the full target within the existing 40 kg/60 L limits. This is not a minimum load size. Finite construction, export, fabrication/refit bills and worker reserve/export targets retain their final small deliveries. Carried loads are not preempted; the policy creates no bodies, stock, or increased rates/capacities.

The new `construction_source_policy: surplus_then_largest_load` protects source operating buffers while useful bulk surplus can supply an accepted construction bill. Existing pickup claims are deducted first. Sources rank by useful surplus, then greatest load bounded by the remaining bill and haul capacity, then access-port-to-site distance and stable source ID. The useful-surplus threshold is the smallest of remaining bill, haul capacity and `courier_min_batch`, so a finite tail is still eligible. If no source has useful surplus, already-reserved materials inside operating buffers remain available to finish the accepted bill. Both focused dispatch/source-selection regressions passed in `Saved/Automation/v09-dispatch-16`, while two AI viability cases failed; [Economy Baseline 0.9](ECONOMY_BASELINE_0_9.md) records these bounded results.

AI policy remains separate from shared simulation rules. In [colony_ai.json](../../AIFILES/colony_ai.json), `core_replication_policy: funded_shortage_first` selects needed, affordable core recipes without replacing paid batches or overriding worker priority; a staffed specialist remains preferred. `bulk_input_policy: remaining_output_bill` budgets useful raw inputs from enabled installed recipes and counts coproducts once, bounded by real purchase limits and credits. Fuel retains its four-buffer, half-target refill policy. The 23-target live plan places the perimeter before industry and bulk storage afterward. These policies govern Starting-AI growth and established-colony operation/rebuilding. Developed setup now loads an explicit initial-state manifest instead of replaying the former 18/36-hour history. Initialization must validate declared assets and physical state without fabricating earned output, trade revenue or elapsed simulation; normal paid rules resume afterward. This new path requires its own native and packaged evidence.

AI placement now has an external `defense_coverage_policy`, `coverage_samples`, `coverage_probe_distance_meters` and `coverage_excluded_roles`. The candidate `prefer_covered_approaches` setting ranks otherwise legal civilian plots by sampled clear approaches from enabled completed fixed platforms' actual equipped weapons, including the prospective body's own occlusion. Road reachability is still checked before any order; ties and all-zero coverage preserve ordinary placement fallback. `defense` and `sensor` exclusions retain their authored perimeter/extension search, and mines remain bound to deposits; since v0.9.2 an armed perimeter plot's ring bearing is chosen to reach the most approaches no fixed gun (finished or under construction) covers, with the authored spread as the tie-break. Coverage is structural geometry, not a claim that guns currently have crew, power or ammunition. It reads no hostile or remote-colony state and creates no resources or completed buildings. `first_legal` remains available for controlled comparison; the new placement regression and scenario acceptance are pending.

Both simulation and neighborhood snapshots now require **format 7**, with matching Rules/AI fingerprints. They retain the shared calendar timestamp, persistent worker-body identities and task/container claims, alongside mine-to-deposit bindings, world offsets, generated nodes/seeds, credits, batteries, recipe transactions, shipments, Rex, roads and material ledgers. The calendar is rebound across every occupied region at live scenario commit; an authored established-colony age does not create a different local sunrise or earned history. Threat flags must be explicit booleans; neighborhood camera/zoom/speed fields are required and validated. Earlier formats and 3× speed migration are intentionally unsupported; rejection requests a new scenario and leaves live state intact. `Interface/ui.json` owns five ordered resource groups and may include only the reserved `road`, `upgrade_road` and `wall` tool entries beyond normal buildable definitions. [Workers, Construction and Transport 0.8](CONSTRUCTION_AND_TRANSPORT_0_8.md) owns the user-facing behavior. The [v0.8.1 record](../verification/v0.8.1.json) retains its 88 reconciled native passes and 117-stage Shipping acceptance as historical evidence. The v0.9 source requires its own broader acceptance; current bounded evidence is listed in [Economy Baseline 0.9](ECONOMY_BASELINE_0_9.md). The [v0.8 record](../verification/v0.8.0.json) retains the preceding release's evidence separately.

The expanded definitions add [energy.json](../../Rules/energy.json), [trade.json](../../Rules/trade.json) and [companions.json](../../Rules/companions.json). Resource quantities use explicit mass and bulk-volume conversion. Recipe input/energy reservation and co-product output capacity are transactional. Road-connected components share generation and batteries; independent networks do not pool energy. Solar generation analytically integrates actual daylight and is zero at night. Core fusion has no daylight multiplier, but completed-core generation still follows actual on-station staffing and workforce efficiency; its rated kW is not an unconditional minimum. [weather.json](../../Graphics/weather.json) only controls presentation, including bounded snow and readable night exposure, without winter economy penalties. Trading ports reserve imported credit and physical cargo volume, and export payments follow actual local cargo delivery and timed shipment. Companion food, movement and morale values remain external. These mechanisms do not establish final economic balance.

The latest expansion adds [walls.json](../../Rules/walls.json) and independent schema-1 [combat](../../Rules/combat.json), [weapons](../../Rules/weapons.json) and [chassis](../../Rules/chassis.json) catalogs. All are validated and fingerprinted. Buildings declare family/level, selectable recipes, time/energy/input multipliers, per-definition staffing mode and inactive-worker storage capability. Cores use proportional staffing so an upgrade can run on its existing crew and manufacture additional staff; other current definitions require full staffing. `stored_workers` is indivisible inventory with mass and volume; recipe `worker_output`, reactivation, trade and recycling share this one physical ledger. Phased construction/length-based road bills exclude discrete bodies because partial installation would otherwise split them. Earlier power-free and refund-free retirement descriptions below are historical boundaries, superseded by these mechanisms.

### Historical v0.7 scenario threat selection

The verified v0.7 package adds two independent scenario settings: `background_bugs` and `periodic_attacks`. Both default to enabled and are selected before scenario initialization. The center and every AI neighbor receive the same choices, including the genuine elapsed simulation used to prepare a developed AI. The settings gate the corresponding existing spawn algorithms; they do not change numerical Rules or AI definitions. Disabled schedules still advance to future deadlines, so saves remain internally consistent without storing an attack backlog. The interface labels a disabled periodic schedule explicitly.

Both simulation format-2 snapshots and neighborhood format-2 metadata persist the settings. A missing pair in an otherwise compatible legacy snapshot means enabled/enabled; partial or non-boolean pairs fail validation. Neighborhood loading also checks that every child snapshot agrees with its metadata before committing any state. Existing Rules and AI fingerprint checks remain mandatory. Scenario choices are runtime state rather than a new Rules schema, so this feature itself does not require a Rules version bump. The final complete v0.7 native suite passed 38 tests cleanly (zero warnings, failed or unrun), including all three new tests for spawn independence, save continuation and real frontend scenario/save flows. Evidence: `Saved/Automation/v07-final/index.json`. The v0.7 Shipping route passed 79 stages with zero failures and exit 0; all nine loose JSON files matched source hashes. See the [verification record](../verification/v0.7.0.json).

### Historical v0.6 presentation schema and interpolation

v0.6 introduced `prototype-6.0` and the retained `stockpile_visual`, `inventory_presentation` and `worker_activity` presentation metadata. These fields select generic bulk/ingot/crate stocks and work/service presentation; they do not replace economic state. Its numerical mechanics and AI definitions were unchanged from v0.5. Static validation passed 32 negative Rules cases and complete configuration checks. All 34 native tests passed cleanly; Shipping passed 79 interaction stages with zero failures and exit 0, recording 831 courier-motion frames between fixed ticks at 1× (`Saved/packaged-v0.6.0-UiSmoke-verification.json`). The current v0.8 schema above supersedes its delivery/port/save limitations.

`FSeigeRenderSnapshot` captures the last authoritative fixed-step state, keyed by courier, enemy and building IDs. Rendering interpolates previous/current positions and construction progress using the fixed-step accumulator fraction, with one step of presentation latency. A newly spawned ID uses its actual current position; removed entities do not acquire another array entry's history. Worker/service animation uses the same interpolated simulation clock. Pausing leaves the fraction and clock fixed. Scenario creation, landing relocation and loading reset snapshot history. This cache is disposable and never serialized as extra simulation authority.

`HasActiveWork` is a read-only projection of real operating conditions: completion/enabled state, staffing efficiency, extractor capacity, recipe inputs/output space, population demand/support and assembly resources, or local service maintenance. The renderer queries it rather than inferring a second economy from animation or diagnostic text. Representative workstations and tool movement do not create agents or carry extra resource stock. Courier payload geometry reads the actual cargo record. `CourierAtLoadingPorts` applies presentation-only endpoint clamps beyond source/target square footprints, including diagonal approaches; cargo is shown waiting at an exterior port while logical travel or a full-destination hold remains inside the building. Open-route interpolation, simulation coordinates, dispatch/arrival clocks, inventory and saves remain unchanged. The clearance is a visual 75 cm, converted by the rendering scale; ports are not newly simulated route nodes. Outdoor stocks use local inventory; site stocks use delivered committed material multiplied by the uninstalled construction fraction. Incorporated material belongs to the same committed bill until completion clears the construction ledger. Actual material transfer remains the existing logistics simulation.

Native regressions `RenderInterpolationByIdentity` and `VisibleWorkUsesOperatingGates` passed, covering ID stability, intermediate-frame positions, reset/pause behavior, exterior-port/yard geometry, unchanged cargo and stalled-work gates. The complete report is `Saved/Automation/v06-final/index.json`. The editor interaction route passed 79 stages with zero failures and recorded 413 courier-motion frames between fixed ticks at 1× speed (`Saved/render-v06-final.log`, `Saved/PresentationSmoke.json`). The Shipping package separately passed 79 stages with zero failures and exit 0, recording 831 courier-motion frames between fixed ticks at 1× (`Saved/packaged-v0.6.0-UiSmoke-verification.json`). These counts establish rendering between authoritative updates in the tested route, not a general frame-rate guarantee. [First Playable Scope](FIRST_PLAYABLE_SCOPE.md) and the development report retain the native/editor/Shipping boundaries. Rule fingerprints change with the metadata schema, so start a new v0.6 scenario; no save migration is claimed.

`SeigeFindExteriorPosition` deterministically searches exterior slots against caller-supplied known living building squares and previously placed piles. Completed outdoor yards use compact indexing of positive inventory entries. Workstations additionally avoid live rendered piles, and their short tool trips reject occupied swept bounds. The caller includes owned home buildings and sensor-visible neighbors (all colonies for observers); hidden buildings do not affect placement. Failed placement omits a model without deleting inventory. This is a presentation-space choice, not a new building placement or logistics rule. Construction scaffold, stacks, body reveal and aggregate workers remain representative rather than a part-by-part construction/path simulation. The dossier reports readable activities and stock locations; exact inventory stays authoritative even when a pile's geometry is simplified.

### Historical v0.5 construction and worker services

The v0.5 implementation introduced Rules `prototype-5.0`; the construction/service fields remain in v0.6. Buildings declare `construction_seconds`, `construction_workers`, `robot_support_capacity` and `staffing_priority`. Policies select `reserved_core_physical_delivery` and `local_capacity_and_maintenance`. The scenario carries an exact `starting_deployment_materials` core kit, separate from operating inventory and escape-shuttle cargo. Native and JS validation check the kit, builders, storage and a viable first support expansion.

An order reserves uncommitted core stock after protecting operating buffers. Materials remain at their physical source until tagged couriers take them to a separate site inventory. Once the full bill arrives, assigned builders advance normalized progress using external time and worker requirements. Completion embodies those materials in the building. Destroyed sites lose their delivered materials; surviving inbound cargo returns to source/core. Lost cargo creates a replacement requirement that waits for real stock.

Construction sites contribute temporary jobs. Automatic staffing uses external `staffing_priority` for both supplied construction and operating jobs, with stable entity order for ties. Current numerical priorities are core 0, service 1, defense 2, sensor 3 and other workplaces 4; lower numbers receive workers first. This preserves service expansion and defenses before general industry without manual job assignment. Paused sites retain reservations. Sites cannot produce, repair, sense or fire before completion. The short core deployment has its carried crew and support; it grants no separate alien-protection period.

Robot growth remains driven by jobs and local assembly inputs, now also bounded by usable support capacity. Completed, enabled and staffed core/service buildings allocate berths and consume local maintenance supplies. Unsupported or unsupplied robots contribute the configured reduced efficiency. Losing capacity does not delete robots; job-driven retirement remains separate. Charging is abstract service capacity, not a simulated power grid or individual battery.

Simulation save format 2 stores construction flags/progress, site materials, courier purpose and maintenance results, together with operating inventories, health, enabled/paused state, production clocks, population/upkeep/dispatch timers, wave and roaming schedules, RNG state, IDs and outcome flags. Staffing and support assignments derive from the saved state. Reservations likewise derive from living site costs minus their delivered materials and tagged incoming cargo; paused sites retain their reservations. Loads parse and validate a temporary candidate before replacing the active colony, including construction consistency and destination payload limits. Outer neighborhood format 2 is independent. Rules/AI fingerprints reject incompatible saves. Developed scenarios run actual construction, logistics, services and threats from a finite seed within external preparation limits. Loading initializes only controller definitions before restoring the snapshot, without replaying preparation.

Historical v0.5 validation passed 29 negative Rules cases and the full configuration check. Its final native suite passed 29 tests (28 clean, one with an Unreal editor background HTTP warning; zero failed or unrun), including construction reservation/delivery, deployment, service expansion/local upkeep, deterministic state continuation and developed setup. Its first-objective scenario succeeded at 435 simulation seconds. Evidence: `Saved/Automation/v05-final/index.json`. The final Shipping route passed 63 stages with zero failures and exit 0; all nine staged JSON files match source byte hashes, and 73 process-tree samples each showed zero TCP/UDP endpoints. These bounded observations and native persistence coverage do not imply a separate packaged save/load roundtrip. See the [development report](../DEVELOPMENT_REPORT.md).

### Weapon and information definitions retained from v0.4

The v0.4 revision introduced `prototype-4.0`. Current definitions retain `weapon_name`, `damage_per_shot`, and `reload_seconds`; nominal DPS is derived as damage divided by reload time. Armed definitions require a name, positive damage, positive attack range, and a reload interval no shorter than the simulation step. Unarmed definitions use an empty weapon name and zero damage, reload, and attack range. A separate `damage_per_second` building override is rejected so the displayed values cannot disagree with combat.

Combat now applies individual shots. A ready weapon fires at the nearest living visible bug in range, then reloads. Staffing/maintenance efficiency changes reload progress, rather than silently changing the displayed damage per shot. Idle time stores one ready shot, not accumulated damage. Building cooldown and its most recent shot event are persisted. Core and turret defaults retain their earlier nominal DPS, but discrete shots change damage timing and overkill; older continuous-combat balance results do not fully validate this revision.

In the historical v0.4 prototype, `power_usage_kw` and `power_generation_kw` were zero for every definition and validators rejected nonzero values because that revision had no power-grid simulation. **That restriction is superseded** by the current road-connected grids and external energy definitions described above. Current dossiers report actual stored energy, generation and consumption; the v0.4 zero-power panels are historical evidence only.

The shared simulation information function supplies six sections for blueprints and live instances: Overview, Weapons, Power, Production, Resources, and Maintenance. It reports construction costs, jobs, health, footprint/ranges, shot damage/reload/DPS, local inventory including required zero-stock inputs, physical inbound cargo, recipe quantities/timing, extraction, repairs, and local support capacity/upkeep. Construction dossiers show required builders, duration, progress and zero-stock cost items. Presentation supplies its distance scale when formatting metre values. The HUD consumes these rows rather than maintaining an independent table of balance values.

Historical v0.4 evidence: the `prototype-4.0` fingerprint intentionally rejected prior-rule saves: start a new scenario. Outer scenario format 2 and optional camera fields do not bypass simulation compatibility. Rules passed static validation and 22 deliberately invalid cases. Final native verification passed 27 tests (26 clean plus one with editor background HTTP warnings), with zero failures/unrun tests. The Shipping route passed 53 stages and exit 0; ten staged files matched source hashes, and 45 process-tree samples each showed zero TCP/UDP endpoints. The failed editor request/retry to `google.com/generate_204` is separate from gameplay assertions and those bounded Shipping observations. See the [development report](../DEVELOPMENT_REPORT.md).

## Validation and reload policy

**Implemented pre-build validation:** Run `node Tools/validate_configuration.mjs` from the project root. [The validator](../../Tools/validate_configuration.mjs) includes the existing Rules checks and validates AI building/resource references, timing and search bounds, established-manifest references/capacities and initial-state bounds, UI building coverage, shortcut conflicts, summary resource IDs, and credits. Graphics validation checks version, numerical bounds, vegetation counts, ordered camera/pad limits, supported terrain resolution, ten nature roles, project asset references, and the supported bundled cloud material. It runs before Unreal in [build.ps1](../../Tools/build.ps1) and in the [GitHub workflow](../../.github/workflows/rules.yml). Invalid definitions fail with a field-specific error rather than silently substituting balance values. Runtime loaders also reject invalid supported definitions. A matching asset package still needs Unreal import/cook and visual checks.

**Verified configuration check:** The current complete definition set passes; focused mutations with unknown AI/UI/resource references, a duplicate shortcut, and invalid AI timing are rejected. These static checks do not prove every AI layout is placeable or an economy survives. Native tests exercise actual placement, production, save continuation, and a first-objective strategy; their results are recorded in the scope.

Not every production cycle is invalid: recycling could intentionally form a loop. The relevant starter check is whether useful production is reachable from actual starting assets and inputs. Do not claim viability from a graph alone without considering labor, throughput, consumption, and physical delivery.

**Current reload policy:** Load a coherent definition set at scenario startup or restart; restart the application after interface or graphics edits. Live hot reload is not implemented. Saves require matching Rules and AI fingerprints. Changing rules underneath existing cargo, queued production, and saved state needs a deliberate migration policy, especially before multiplayer.

**Packaging contract:** [The module build file](../../Source/Seige/Seige.Build.cs) stages `Rules`, `AIFILES`, `Interface`, and `Graphics` as loose files beside the target binary. The runtime first checks the project directory, then the executable directory. Keep these folders with the packaged executable. v0.5 verified all nine external JSON files byte-identical to source and loaded them in its packaged 63-stage interaction check. Historically, v0.4 verified ten loose files and passed 53 stages. The earlier v0.3 package separately passed its 28-stage route. v0.2 separately passed a controlled packaged balance edit; that edit experiment was not repeated for v0.3. Evidence is recorded in the [development report](../DEVELOPMENT_REPORT.md).

## State, saving, and future multiplayer

**Current local ownership:** Each occupied scenario cell owns an independent simulation instance. The center is human-controlled or AI-controlled for observation; up to eight neighbors run the same economy and local threat rules. Local inventories and power grids remain separate. The implemented privateer bridge moves player-owned fleet units between sectors, resolves foreign combat/cargo capture and returns surviving units and goods without changing fleet ownership. This does not provide general inter-colony trade, supply convoys, shared inventory or multiplayer authority.

The scenario clock advances only during active play while unpaused. Setup, human core placement, main menu, settings, and credits do not advance colony simulations. Core placement uses the simulation's placement validation before play starts. These confirmed single-player controls do not determine how a future persistent server behaves.

Local save/load writes the center and occupied neighbor snapshots with scenario slots, camera, speed, pause state, and AI fingerprints. A generation directory and atomic metadata replacement protect the active save from partial writes. Loading validates all candidate snapshots before replacing live state. Native continuation and neighborhood save/load tests have passed; long-term migration and recovery guarantees remain later work.

**Verified v0.3 extension:** Camera yaw and pitch are optional format-2 fields, with bounded validation and stable defaults for older saves. Logical simulation coordinates stay unchanged while presentation maps each unit to six Unreal centimeters. Native tests cover camera/terrain mathematics and saved orbit compatibility; the packaged rendered route covers actual perspective interactions. No separate v0.3 packaged save/load roundtrip was run. Native success and packaged interaction success establish those distinct boundaries, not a long-term migration guarantee.

**Recommended future boundary:** Reuse the definition model and command/state concepts when choosing authoritative multiplayer execution. Clients would submit intentions; the authoritative owner would resolve shared inventories, production, combat, and travel. A trusted service remains an architectural proposal, not a user-selected deployment or networking design.

Before persistent multiplayer, resolve ruleset versions, save migration, command validation, cross-sector transactions, reconnects, offline simulation, and relocation transfer ownership. These are future engineering tasks, not automatic benefits of using external JSON or a local subsystem. Local editable balance files do not imply that multiplayer clients can alter authoritative balance.

## Prototype deviations must remain explicit

Current v0.9 source uses persistent finite worker bodies for operating, construction and physically routed cargo tasks. Partially delivered bills can advance work; delivered and installed material remain distinct. Construction cancellation/refunds and manual individual-worker orders remain absent. Road-connected electricity, batteries, inactive-worker storage/recycling, external trade and combat/fleet modules are implemented in source. Vehicle travel samples terrain grade, but this does not provide a full traffic system. Finite local AI, provisional dispatch/threat/balance rules, limited mission behavior and incomplete robot needs remain prototype boundaries. The [v0.8.1 record](../verification/v0.8.1.json) records the preceding release; it does not verify the new worker or dispatch implementation.

Externalizing these choices makes them easier to tune; it does not make them approved final game rules. Keep observed implementation behavior, candidate design, and verified test results distinct.
